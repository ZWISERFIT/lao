## 1. B1 — Verify 恒真缺陷（审计最严重缺陷）

### 根因
`verify()`（旧 agent.py:327-336）调用 `_read_proc_stat_cpu()`——单次读 `/proc/stat` 算出的是**开机以来平均 CPU**（本机实测 ≈26%，永远低于 70% 的 `CPU_VERIFY_BELOW`）→ verify 恒真 → 27 条 `verified:true` 全部不可信（铁证：`17:39:50 verified:true` → `17:40:20 cpu 100%`）。

### 修复（ris/agent.py）
1. 新增 `_instant_cpu_percent(interval)`：**独立瞬时采样**——psutil 实时优先；psutil 缺失时 `/proc/stat` 双读差分（真增量，非开机均值）。
2. `recover_cpu.verify()` 重写：`settle_s`（默认 5s）回落观察窗 + 瞬时重采样；旧函数被明令"禁止用于 Verify"并加注释警示。
3. Verify 证据入事件：`detail.verify_method="resample-instant"`、`detail.cpu_after_recover=<实测值>`（对齐审计 §6.3 schema 的 `lifecycle.verify_method` 要求）。
4. 次级缺陷同修：CPU 仍高时事件 `status="failed"`（不再被记为成功）；恢复失败也落事件（此前只有成功才落）。

### 测试证据（anti-tautology 铁证）
```
test_verify_fails_while_cpu_still_high:
  注入 恢复后 CPU=95% → attempts=2(动作真实执行) / recovered=False / verified=False
  ← 旧实现在同一场景下 verified=True(开机均值 26%<70%)·这是恒真缺陷的直接反证
test_verify_passes_only_after_real_drop:
  注入 [95%, 40%] → 第2次尝试通过·cpu_after_recover=40.0·持续帧状态机复位
test_proc_fallback_is_delta_not_boot_average: /proc 双读差分兜底·值域合法
```

## 5. B5 — Provider 隔离/降级真实实现

### 修复（ris/provider.py 重写为 `ProviderIsolator` 熔断器 + 两端接线）
1. **抖动抑制**：连续 `CONFIRM_FAILURES=2` 帧探活失败才隔离（单帧网络抖动不误杀·治审计 B10）。
2. **状态持久化**：`shared/state/provider-isolation.json`（主循环每 30s 重建对象·状态靠文件续命）。
3. **冷却半开**：`ISOLATION_COOLDOWN_S=600` 到期自动半开灰度回归；探活恢复可提前释放（`status="released"` 事件）。
4. **RIS 主循环接线**（agent.check_once）：`provider_unavailable` → `record_failure`；`provider_ok` → `record_success`（ok 事件本身不落日志·防刷屏）；LAO-signal 的错误率退化同样喂入熔断器。
5. **LAO 侧真实降级**：隔离指令经 ris-bridge `summary.isolated_providers` → `_ris_guard_provider` 摘除候选/切换健康 provider/全阻断则 503——**成本事故链路（provider掉线→回退直连→成本暴涨）从"事件里被注释"变成"路由层被阻断"**。
